## 3. いま利用者に起きていること（今回直したもの）

技術的な分類ではなく、**利用者に何が起きるか**で並べています。

### 🔴 ① 応募したのに、応募が消える（最も重大）

**症状**: 通信が切れたとき・ログインの期限が切れたときなどに、応募が保存されていないのに **「応募を受け付けました」と表示**されていました。

**なぜ危ないか**:
- 求職者は「応募した」と信じて、連絡を待ち続けます
- データベースに応募は無く、**スタッフへの通知メールも飛びません**
- **誰も気づけません。** 後から復元することもできません

これは求人紹介という事業の**唯一のコンバージョン（成果地点）が静かに消える**という意味で、最も損害の大きい欠陥でした。

> 中国の求職者にとって「0円」という訴えは、それ自体が疑いの対象になりやすいものです（無料をうたう悪質な業者が実在するため）。**エラーが出るよりも、「申请成功」と出たのに誰からも連絡が来ないほうが、はるかに深刻です**。詐欺と区別がつかないからです。

**対応**: 成功したときだけ完了を表示し、失敗は理由別に伝えて再試行できるようにしました（PR #55）。

### 🔴 ② ログイン中なのに「会員登録が必要です」と言われる

通信が不安定なときに、**ログイン済みの会員へ再登録を促していました**。中国のモバイル回線では起こりやすい状況です。あわせて、通信が切れると**読み込み中のまま永久に止まる**経路もありました。（PR #55）

### 🔴 ③ パスワードを忘れると、二度とログインできない

会員が自分でパスワードを再設定する機能がありません。しかも**利用規約 第6条2項で「WeChatで申し出れば再設定します」と約束しているのに、その窓口への行き方がサイト上にありませんでした**（WeChat IDはログインが必要な画面にしか出ていなかったため）。

**対応**: ログイン画面に問い合わせ窓口を追加（PR #55）＋ スタッフ向けの対応手順を新設（`docs/ops/password-reset-guide.md`）。
⚠️ **これは応急処置です。** 限界と改善計画は同手順書の末尾に書いてあります（**8/18までにマイページへ「パスワードを変更する」を追加することを推奨**）。

### 🔴 ④ WeChatの窓口が、QR・IDとも実物ではなかった

**サポート窓口は2か所とも本物ではありませんでした。** このサイトの主要な連絡手段であり、利用規約 第6条2項では「WeChatで申し出ればパスワードを再設定する」と会員に約束している窓口です。

| | 何が載っていたか |
|---|---|
| **QRコード** | 四角い点を計算式で散らしただけの**図形**（開発中の仮置き）。読み取っても何も起きません。中国の利用者にとって、壊れたQRは**悪質な業者のサイトに見える強いサイン**です |
| **ID** | `yingpin-support` という、**御社のものではないID**。第三者が実際に取得していた場合、利用者は**赤の他人を友だち追加します** |

**QRは解消しました。** 7/31にオーナーから正しい画像をいただき、読み取り先がWeChatの友だち追加リンクであることを機械的に確認したうえで掲載しています（圧縮ノイズを除去して107KB→3.6KBに縮小。中国の回線で効きます）。

**IDはまだ出せません。** いただいた `wxid_…` はWeChatの内部管理番号で、**検索欄に入れても見つかりません**。載せればダミーQRと同じ行き止まりになるため、**検索できる「微信号」が設定されるまでは表示しない**設計にしてあります（`wechat-qr-guide.md` ①）。

> 📌 なお **WeChatの友だち追加QRは、IDから計算で作ることができません**（アカウント固有のデータを持つため）。**QR作成サイトなどで作り直さないでください。**

### 🟡 ⑤ 「演示版（デモ版）」と表示される

ログアウトの確認画面に、開発中の文言が残っていました。有料職業紹介事業者のサイトが自ら「デモ版」と名乗っている状態でした。（PR #55）

### 🟡 ⑥ 読み込み中・失敗・0件が、すべて同じ画面

求人一覧・お気に入り・マイページで、**取得に失敗しても「0件です」と表示**していました。利用者からは「求人が無いサイト」「お気に入りが消えた」「応募履歴が消えた」ように見えます。（PR #56）

### 🟡 ⑦ エラー画面・404画面が無い

存在しないURLを開いたときなどに、**Next.js既定の英語の画面**が出ていました。会員側は中国語が既定なのに、障害時だけ英語になる状態でした。（PR #56）

### 🟡 ⑧ 管理画面で「権限がありません」と誤って出る

データベースに繋がらないときも「権限がありません」と表示していました。原因が正反対なので、**スタッフが「自分の権限が外された」と誤解します**。（PR #56）

## 4. すでに影響が出ていないかの確認（お願い）

サイトは**サンプル求人だけを載せた状態で、すでに公開・登録可能**でした。実在の求職者が登録・応募していた可能性があります。

**次を確認してください**（3分）:

1. `https://yingpin.jp/admin` を開く
2. **「会員数」が0でなければ**、`/admin/members` で誰が登録しているか確認
3. **「新規応募（未対応）」が0でなければ**、`/admin/applications` で確認

**1件でもあれば、その方に個別に連絡してください。** サンプル（架空）の求人に応募された可能性があり、放置すると「応募したのに無視された」という体験になります。

## 7. 法務・事業のリスク（把握しておいてほしいこと）

### ① 弁護士の回答が、本格稼働より後になります

顧問弁護士への確認事項のうち、**「中国在住者に日本から直接募集をかけてよいか」（論点B-1）は、回答の目安が9月上旬**です。本格稼働（8/18）より後になります。

**サイトの実装は現在の方針で進めて問題ありませんが、回答次第で募集方法の見直しが必要になる可能性がある**ことは、意思決定の前提として持っておいてください。

### ② 仮パスワードをWeChatで伝える運用

現在パスワードを再設定するには、スタッフが決めたパスワードをWeChatのチャットで伝えるしかありません。**そのパスワードは履歴に残り続けます**（会員が自分で変更する機能が無いため）。個人情報の安全管理措置の観点で弱く、9月の弁護士レビューで指摘され得る論点です。→ 8/18までの改善を推奨します。

### ③ サンプル求人の掲載

有料職業紹介事業者が実在しない求人を掲載している状態は、職業安定法（第5条の4「的確な表示」・第65条「虚偽の広告」）の観点から望ましくありません。**8/8を待たず、今すぐ非公開にすることを推奨します**（データは消えません）。

### ④ 退会・データ削除の手順が未整備

会員から「退会したい」「データを消してほしい」と言われたときの手順書がまだありません（GitHub Issue #33）。プライバシーポリシーを公開している以上、**8/18までには用意すべき**です。

## 9. 良かった点（率直に評価して）

**この規模のプロジェクトとしては、土台の作り込みが例外的に高い水準です。** 以下はいずれも、経験の浅い開発では抜けやすいところです。

| 項目 | なぜ良いか |
|---|---|
| **管理者用の万能キーを一切使っていない** | `service_role`（全データを触れる鍵）がコードにも設定にも存在しません。漏れたら終わり、という最悪の事故が構造的に起こりません |
| **社内メモを別のテーブルに分けた** | 「行は守れても列は守れない」というデータベースの性質を正しく理解した対処です。画面で隠すだけでは、会員がブラウザから直接読めてしまいました |
| **本人確認フラグ・会員番号をDB側でロック** | 会員が自分で「確認済み」にすることを、アプリではなくデータベースで防いでいます |
| **会員番号を「その日の連番」にした** | 乱数だと衝突して登録が失敗し、**その電話番号が二度と使えなくなる**問題がありました。確率を下げたのではなく、原理的に起こらない形に変えています |
| **同意の記録を「追記しかできない」設計に** | スタッフでも書き換え・削除ができません。証拠として意味を持つ形です |
| **パスワードの長さを「文字数」でなく「バイト数」で判定** | 中国語話者が漢字を含むパスワードを使う場合を想定した配慮です |
| **法務文書の11分野が3か所で一致しないとビルドが失敗** | 条文だけ直して画面を直し忘れる、という食い違いを機械が止めます |
| **日本語・中国語の文言が完全に対応** | 309キーすべてで欠落ゼロ。片方だけ足すと中国語画面に日本語が出るので、地道ですが重要です |
| **外部サービスへの依存がゼロ**（実測） | 中国からのアクセスで問題になる外部の読み込みが**1件もありません**。トップページの転送量も一般的な範囲です。中国向けサイトとして重要な土台ができています |

### B. 依存パッケージの脆弱性について

`npm audit` で **high 12件**が報告されますが、**対応は不要かつ不可能**です。

- 内容は `postcss` と `sharp`（Next.js が内部で使うもの）
- **修正済みの安定版が存在しません**（最新の 16.2.12 も対象範囲内）
- 自動修正を実行すると **Next.js 9系まで巻き戻される**破壊的変更になります
- **実害はほぼありません**: `sharp` は画像最適化用ですが**このサイトは画像を1枚も使っていません**。`postcss` はビルド時のみ動作します

→ 提案: **dependabot（更新の自動通知）を設定**し、修正版が出たら気づけるようにする。CIに `npm audit` を足すのは、いま入れると常に赤くなるため非推奨。

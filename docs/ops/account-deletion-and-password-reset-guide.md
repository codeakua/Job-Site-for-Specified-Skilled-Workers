# 会員の退会（アカウント削除）とパスワード再設定の手順

> **この手順でできること**: 会員から「退会したい（アカウントを消してほしい）」「パスワードを忘れた」と申し出があったときに、**法律に反しない形で**対応できます。
> - **やる人**: ①申し出の受付と本人確認 → **会員対応のスタッフ** ／ ②Supabaseの操作 → **サイトの管理者（Supabaseにログインできる方）**
> - **所要時間**: 退会・削除＝**30〜40分**（会員1人あたり）／パスワード再設定＝**15分**（会員1人あたり）
> - **必要なもの**: Supabaseのログイン情報／会員のWeChat／会員番号・氏名・生年月日
> - 途中で分からなくなったら、**その画面をそのままClaudeに見せてください**。どこを押せばよいか案内します。
>
> **この手順書が果たしている約束**: プライバシーポリシー**第10条**（開示・訂正・利用停止・削除等の請求）・**第11条**（退会とデータの消去）、利用規約**第6条第2項**（パスワードの再設定）・**第19条**（退会）。トップページにも「登録・退会はいつでも自由」と掲げています。**会員に約束した以上、申し出が来たその日に調べ始めるのでは間に合いません。**

## 0. 最初に読む — この2つは性質がまったく違います

| | **退会・アカウント削除** | **パスワードの再設定** |
|---|---|---|
| やり直し | ⛔ **できません。** 消したデータは戻りません | ✅ できます。間違えても、もう一度やり直せる |
| 法律の制約 | 🔴 **あります。** 「全部すぐ消す」と**職業安定法違反**になります（→ 第2部） | ありません |
| 急ぐべきか | 急がないでください。**期限は30日**あります | できるだけ早く（会員はサイトを使えない状態です） |
| 迷ったとき | **止めて、オーナーに相談する** | Claudeに画面を見せて確認する |

**どちらも、最初にやることは同じ「本人確認」です。** 次の第1部を必ず先に読んでください。

> **この手順書が扱わないこと**: 会員情報の**訂正**（住所が変わった等）と**開示請求**（自分の情報を見せてほしい）。開示請求のときは、第2部ステップ3の「書き出しSQL」がそのまま使えます（消さずに書き出して、会員本人にお渡しします）。訂正が必要なときは、内容をオーナーに伝えて判断を仰いでください。

# 第1部【共通】本人確認のしかた（必ず最初に）

## 1-1. なぜ、ここを厳しくやるのか

> ### 🚨 このサイトには「電話番号を本当に持っている」ことの証明がありません
>
> 多くのサイトは、登録時にSMS（ショートメール）で数字を送り、それを入力させることで「この電話番号は本人のものだ」と確かめています。**このサイトはSMS認証を使っていません**（コストと中国からの到達性の問題のため。プライバシーポリシー第2条にも明記しています）。
>
> つまり、**誰かが他人の電話番号を勝手に入力して登録することを、システムは止められません。**
>
> そのため、**スタッフがWeChatで行う本人確認（管理画面の「本人確認済み」＝ `verified` フラグ）が、この会員が本人であることを担保する唯一の手段**です。ここが崩れると、
>
> - **パスワード再設定**では、他人にアカウントを乗っ取られます（＝その人の氏名・生年月日・住所・応募履歴がすべて渡ります）
> - **退会・削除**では、他人の申し出で会員のデータを消してしまいます（＝**取り消せません**）
>
> **「システムが守ってくれる」部分が無いので、人が守るしかありません。** これがこの章の位置づけです。

## 1-2. 手順（3つ照合する）

プライバシーポリシー第10条第2項で、会員に次のとおり約束しています。**この2つを両方満たすまで、作業を始めてはいけません。**

**① 申し出の経路を確かめる**

- **登録済みのWeChat ID**、または**登録済みの電話番号**から申し出があったこと
- または、窓口メール `yazawa-y@partner-japan.biz` に届いた申し出であること

**② 会員本人にしか答えられない3点を照合する**

会員に次の3つを送ってもらい、管理画面 `/admin/members` の登録内容と**1文字ずつ**見比べます。

| 照合する項目 | 見る場所 | 注意 |
|---|---|---|
| **会員番号**（`YP-` で始まる） | `/admin/members` の「会員番号」 | 覚えていない会員も多い。無い場合は電話番号で代替する |
| **氏名** | 同「氏名」 | 登録時の表記と一致するか（簡体字・繁体字の違いに注意） |
| **生年月日** | 会員の行を開いた詳細 | **ここがいちばん重要。** 生年月日は他人が知りにくい |

> **会員番号を覚えていない場合**は、**登録時に入力した電話番号（国番号を含み、先頭の `0` を付けたかどうかも含めて）**を答えてもらい、それで代替します。**代替してよいのは会員番号だけです。氏名と生年月日は必ず照合してください。**

## 1-3. 受け付けてよい申し出・いけない申し出

| 状況 | 判断 |
|---|---|
| 登録済みのWeChatから、3点すべてが一致した | ✅ 進めてよい |
| 3点のうち**生年月日が違う** | ⛔ **進めない。** もう一度確認し、それでも合わなければ断る |
| 「本人の家族です」「代理です」 | ⛔ **進めない。** オーナーに相談（委任状等の判断が要ります） |
| 登録していないWeChat・電話番号からの申し出 | ⛔ **進めない。** 登録済みの経路から連絡するよう案内する |
| 「本人確認済み」になっていない会員からの申し出 | ⚠️ **止めて、オーナーに相談。** WeChat確認をまだ受けていない人なので、本人性の裏づけがいちばん弱い |
| メールだけで来た申し出（WeChatでの確認ができない） | ⚠️ **止めて、オーナーに相談。** 登録済みWeChatに当社から連絡し、そこで確認できるまで進めない |

> **急かされても、手順を飛ばさないでください。** 「急いでいる」「すぐ消して」と言われても、**削除には法律上30日の猶予があります**（プライバシーポリシー第10条第4項・第11条第2項）。本人確認より急ぐ理由はありません。

## 1-4. 確認したことを記録する

照合が終わったら、次の1行をその場でメモしてください（あとで台帳に転記します）。

```
2026-09-01 14:20 WeChat（ID: wx_xxxxx）より退会の申し出。
会員番号 YP-20260810-1003・氏名・生年月日の3点一致を確認。確認者: 田中
```

# 第2部【退会・アカウント削除】

## 2-1. 🔴 いちばん大事な考え方 — 「全部すぐ消す」と、今度は職業安定法違反になります

会員から削除を求められたとき、**すべてを消してはいけません。**

当社は有料職業紹介事業者（許可番号 11-ユ-301340）です。**職業安定法第32条の15**により、**求人求職管理簿**（求職者を受け付け、どう紹介したかの記録）を**2年間保存する義務**があります。

つまり、次の2つの法律が正面からぶつかります。

| | 求めること |
|---|---|
| **個人情報保護法**（＋当社のプライバシーポリシー第11条） | 会員が求めたら、個人データを**消す** |
| **職業安定法 第32条の15** | 求人求職管理簿を**2年間残す** |

**この衝突をどう捌くかが、この手順書のいちばん重要な部分です。** 当社の整理は次のとおりです。

> ### ✅ 当社の整理: **「残す義務のある記録だけを分けて保管し、それ以外は消す」**
>
> 1. 帳簿として残すべき記録を、**データベースの外へ書き出す**（CSVファイル）
> 2. 書き出したファイルを、**普段の業務では使わない場所へ分けて保管する**（＝プライバシーポリシー第11条第3項でいう「他の情報と分離して保管」）
> 3. **データベースからは、その会員のデータをすべて消す**（ログインもできなくなる）
> 4. **2年が経ったら、書き出したファイルも消す**
>
> この扱いは、**個人情報保護法第35条第5項**（法令に基づく場合は利用停止等に応じる必要がない）に基づくものとして、プライバシーポリシー第11条第4項に明記済みです。

**保存期間の数え方（当社の運用）**

| 項目 | 当社の決め |
|---|---|
| 起算日 | **削除を実行した日**（＝退会により求職の申込みが終了した日） |
| 満了日 | **その2年後の同じ日**（例: 2026年9月1日に削除 → **2028年9月1日**） |
| 満了したら | 書き出したファイルを消し、台帳に消去日を書く（→ 2-8） |

> ⚠️ **弁護士に確認中の点**: 起算日の考え方（「求職の申込みの有効期間の終了後」の解釈）は、確認論点リストの **B-5 ①** で顧問弁護士に確認しています（回答の目安は2026年9月上旬）。**回答が来るまでは、上の当社案どおり「削除実行日から2年」で運用してください。** 回答によって期間の数え方が変わった場合は、台帳の「満了日」を書き直します（**台帳に満了日を書いておくのは、このためでもあります**）。
>
> 同じく **B-5 ③**（帳簿として残すべき項目が足りているか）の回答によっては、2-4 で書き出す項目を絞ります。**現時点では「多めに書き出して分離保管する」ほうを選んでいます**（足りないと職業安定法違反になり、あとから取り返せないため）。

## 2-2. 何を消すのか（技術的な事実）

会員1人のデータは、次の場所に分かれて入っています。

| 場所 | 中身 |
|---|---|
| **`auth.users`**（ログインアカウント） | 電話番号から作った内部アドレス・パスワード（暗号化済み） |
| **`members`**（会員情報） | 会員番号・氏名・生年月日・住所・電話番号・WeChat ID など |
| `applications`（応募） | どの求人にいつ応募したか・対応状況 |
| `application_staff_notes`（スタッフの対応記録） | 応募ごとのスタッフメモ。**求人企業への同意取得の記録もここに書かれます** |
| `favorites`（お気に入り） | 保存した求人 |
| `member_consents`（同意の記録） | 規約・ポリシーへの同意日時と版数 |

> ### 📌 実は、**Supabaseの画面で「ログインアカウント」を消すだけで、全部まとめて消えます**
>
> データベースが「**会員情報はログインアカウントにぶら下がっている**」という作りになっているため（専門用語で `on delete cascade` ＝連鎖削除）、`auth.users` の1行を消すと、`members` → `applications` → `application_staff_notes` / `favorites` / `member_consents` の順に、**自動的にすべて消えます**。
>
> **だから、手順は「ログインアカウントを1回消す」だけで足ります。** 順番を間違える余地がないので、これがいちばん安全です。

> ### ⛔ **逆はダメです。`delete from members` だけを実行しないでください**
>
> `members` だけを消すと、**ログインアカウント（`auth.users`）が残ります。** すると、
>
> - その人は**ログインできてしまう**のに、**会員情報が無い**という壊れた状態になります
> - その電話番号は**登録済み扱い**なので、他の人も使えません
>
> （※ このサイトには、この壊れた状態から自動で復旧する仕組みが一応入っています。同じ電話番号・**同じパスワード**でもう一度登録すると会員情報が作り直されます。しかし退会した人がパスワードを覚えている保証はなく、**当てにできません**。）
>
> **消すのは「ログインアカウント」から。これだけ覚えてください。**

## 2-3. 手順の全体像（7ステップ）

| ステップ | やること | 誰がやるか |

## 2-5. ステップ3: 残す記録を書き出す（SQL 3本）

> **ここから先はSupabaseの操作です。** 左メニューの **SQL Editor**（エスキューエル・エディタ）→ **New query**（新しいクエリ）に貼り付けて、右上の緑の **Run**（実行）ボタンを押します。
>
> 🚨 **SQL Editor では、この手順書に書かれたSQL以外を実行しないでください。** これは `staff-registration-guide.md` 第9章からの、当社の変わらない約束です。特に `drop`・`truncate`・条件（`where`）を外した `delete` は、**データが元に戻せなくなります**。

### まず、その会員のUIDを調べます

**UID**（ユーアイディー）とは、`a7d3e5f1-2b90-…` のような、その人専用の背番号です。**以降のSQLは、すべてこのUIDで対象を指定します**（氏名で指定すると同姓同名の他人を巻き込むため）。

> #### 🔍 このSQLを実行すると何が起きるか
> **表示するだけです。何も変わりません。** 会員番号を手がかりに、その人のUIDと登録内容を1行だけ表示します。

```sql
-- 【読むだけ・データは変わりません】会員番号からUIDと本人確認用の情報を出す
select m.id                                as "UID（以降のSQLで使います）",
       m.member_no                         as "会員番号",
       m.last_name || ' ' || m.first_name  as "氏名",
       m.birth                             as "生年月日",
       m.phone_code || ' ' || m.phone      as "電話番号",
       m.wechat_id                         as "WeChat ID",
       m.verified                          as "本人確認済み",
       u.email                             as "ログイン用の内部アドレス"
  from members m
  join auth.users u on u.id = m.id
 where m.member_no = 'YP-20260810-1003';   -- ← ここを対象の会員番号に書き換える
```

**表示された「氏名」「生年月日」が、第1部で照合した内容と一致していることを、ここでもう一度目で確認してください。** 一致しなければ**先に進まないでください**（会員番号の打ち間違いです）。

# 第3部【パスワードの再設定】

## 3-1. なぜ自動でできないのか

このサイトは、登録に**実在のメールアドレスを使っていません**。電話番号から `p819012345678@phone.yingpin.app` という**架空のアドレス**を内部で組み立てて、それをログインIDとして使っています。

**架空のアドレスなので、再設定メールを送っても誰にも届きません。** そのため、よくある「パスワードをお忘れですか？ → メールを送る」という仕組みが**使えません**。

このことは、**利用規約 第6条第2項**にあらかじめ明記してあります。

> 本サービスは登録にメールアドレスの実在確認を用いないため、パスワードを失念した場合の、メール送信による自動的な再設定は行いません。この場合、会員は登録済みのWeChat IDを通じて当社に申し出るものとし、当社は登録情報との照合により本人であることを確認したうえで、**仮パスワードの発行その他の方法により再設定に対応します**。

**つまり、スタッフの手作業が前提の設計です。** その手作業がこの第3部です。

```sql
       m.member_no                         as "会員番号",
       m.last_name || ' ' || m.first_name  as "氏名",
       m.birth                             as "生年月日",
       m.phone_code || ' ' || m.phone      as "電話番号",
       m.wechat_id                         as "WeChat ID",
       m.verified                          as "本人確認済み"
  from members m
 where m.phone_code = '+81'          -- ← 国番号（中国なら '+86'）
   and m.phone      = '90-1234-5678'; -- ← 登録時に入力されたとおりの表記
```

> **0行になった場合**は、電話番号の書き方が登録時と違います（ハイフンの有無・先頭の `0` の有無）。**推測で書き換えず、会員に「登録したときに入力したとおり」をもう一度聞いてください。**

### ステップ3: 仮パスワードを決める

| ルール | 理由 |
|---|---|
| **8文字以上、英字と数字の両方を含む** | Supabase側の設定（`supabase-auth-policy-guide.md` ①）と一致させる。満たさないと**ログインできません** |
| **会員ごとに違うものにする。使い回さない** | 1人分が漏れたときに、他の会員へ広がらないようにする |
| **その場で作り、台帳やメモに残さない** | 台帳に平文で書くと、台帳そのものが「全員のパスワード一覧」になります |
| 例: `ypTemp2609a`（そのまま使わず、必ず変えてください） | |

> ### ⚠️ **このサイトには、会員が自分でパスワードを変更する画面がまだありません**
>
> つまり、**発行した仮パスワードは、次に再設定するまでその会員のパスワードであり続けます。** スタッフが知っているパスワードのままになる、ということです。
>
> **だからこそ、上の3つのルール（使い回さない・記録に残さない・その場で作る）を必ず守ってください。**
>
> 💡 **将来の改善案（実装は未着手）**: マイページに「パスワードを変更する」画面を作れば、会員が自分で変えられるようになり、この問題は無くなります。オーナーの判断でIssueを立てる候補です。

### ステップ4: パスワードを書き換える（SQL）

> #### 🔍 このSQLを実行すると何が起きるか
> **⚠️ これは「変える」SQLです。** 指定したUIDの会員のパスワードが、**その場で新しい仮パスワードに置き換わります。**
> - **元のパスワードは戻せません**（暗号化されていて、当社の誰も元の値を知らないためです）。ただし、**もう一度このSQLを実行すれば何度でも変えられる**ので、取り返しがつかない操作ではありません
> - **消えるものは何もありません。** 会員情報・応募・お気に入りには一切触れません
> - **UIDを間違えると、他人のパスワードを変えてしまいます**（その人はログインできなくなります）。**実行前にUIDをもう一度確認してください**

```sql
-- 【変わります】指定した会員のパスワードを仮パスワードに置き換える
update auth.users
   set encrypted_password = crypt('ここに仮パスワード', gen_salt('bf')),
       updated_at         = now()
 where id = 'ここにUIDを貼る';
```

実行後、下に **`Success. No rows returned`** と出れば完了です。

> **`function crypt(...) does not exist` というエラーが出た場合**は、`crypt` を `extensions.crypt` に、`gen_salt` を `extensions.gen_salt` に書き換えて、もう一度実行してください。それでも出る場合は、**エラーの文言をそのままClaudeに伝えてください。**

### ステップ5: 書き換わったことを確認する

> #### 🔍 このSQLを実行すると何が起きるか
> **確かめるだけです。何も変わりません。** 「いま設定したパスワードで一致するか」を判定して `true` / `false` を返します。**パスワードそのものは表示されません**（暗号化されていて取り出せないため）。

```sql
-- 【読むだけ・データは変わりません】仮パスワードが正しく入ったかの確認（true が正解）
select (encrypted_password = crypt('ここに仮パスワード', encrypted_password)) as "この仮パスワードで一致するか"
  from auth.users
 where id = 'ここにUIDを貼る';
```

**`true` と表示されれば成功です。** `false` なら、ステップ4で入力した仮パスワードと、ここに入力した仮パスワードが違っています（打ち間違い）。ステップ4からやり直してください。

## 3-3. 乗っ取りが疑われるとき

会員から「**自分は何もしていないのに応募した覚えのない求人に応募されている**」「**知らない間にログインされている**」といった申し出があった場合は、パスワードを変えるだけでは足りません。**相手がすでにログインしている状態は、パスワードを変えても続きます。**

その場合は、ステップ4のあとに次を追加で実行してください。

> #### 🔍 このSQLを実行すると何が起きるか
> **⚠️ これは「消す」SQLですが、消えるのは「ログインしている状態」だけです。** 会員情報・応募・お気に入りには一切触れません。
> 実行すると、その会員としてログインしている**すべての端末が強制的にログアウト**されます（会員本人のスマホも含みます）。会員には、新しい仮パスワードで入り直してもらってください。

```sql
-- 【変わります】この会員のログイン状態をすべて解除する（全端末からログアウト）
delete from auth.sessions where user_id = 'ここにUIDを貼る';
```

そのうえで、**必ずオーナーに報告してください。** 漏えいの疑いがある場合は、プライバシーポリシー第13条（個人情報保護委員会への報告・本人への通知）の対象になる可能性があり、**スタッフの判断で終わらせてよい事案ではありません。**

> `relation "auth.sessions" does not exist` のようなエラーが出た場合は、**何もせずClaudeに伝えてください**（Supabase側の作りが変わっている可能性があります）。

# 第4部 絶対に触ってはいけない設定

> ## 🚨 **`Confirm email`（メール確認）は、OFFのまま絶対に触らないでください**
>
> この項目を **ON** にすると、Supabaseは「**確認メールを送って、本人がリンクを踏むまで登録を完了させない**」動きに変わります。
>
> ところが、このサイトが使っているのは `@phone.yingpin.app` という**架空のアドレス**です。**そのメールは誰にも届きません。**
>
> **何が起きるか**
>
> 1. **新規登録が全員できなくなります。** 会員も、スタッフも、テスト登録も、すべてです
> 2. さらに悪いことに、**登録を試みた人のログインアカウント（`auth.users` の行）だけが中途半端に残ります**
> 3. その結果、**その電話番号では二度と登録もログインもできなくなります**（ロックアウト）
>
> **回復方法**: Supabaseの **Authentication → Users** から、その中途半端に残った行を **Delete user** で削除すれば、その電話番号は再び使えるようになります。**設定を戻すだけでは、既にできてしまった行は消えません。**
>
> ⚠️ **「既定でOFFだから触らなくてよい」とは考えないでください。** 新しく作ったプロジェクトでは**最初からONになっていることがあります**（2026年7月の東京移設時に実際に確認しました）。
>
> 📌 **この手順書に関係する理由**: 第2部・第3部の作業では、**Authentication の画面を開きます。** その画面の並びに、この設定があります。**目的の操作（Delete user）以外は、何も押さないでください。**
>
> 詳しくは `docs/ops/supabase-auth-policy-guide.md` の「作業前に必ず読んでください」と、`docs/progress.md` §24 を参照してください。

# 第5部 やってはいけないこと（まとめ）

1. ⛔ **本人確認をせずに、削除やパスワード再設定をしない。** SMS認証が無いこのサイトでは、**本人確認だけが唯一の防波堤**です（第1部）
2. ⛔ **書き出し（第2部ステップ3）をせずに削除しない。** 職業安定法第32条の15の保存義務を果たせなくなり、**あとから復元できません**
3. ⛔ **`delete from members` だけを実行しない。** ログインできるのに会員情報が無い、壊れた状態になります（2-2）
4. ⛔ **`where` の条件を消したり、書き換えずに実行したりしない。** `delete from members;`（条件なし）は**全会員を消します**
5. ⛔ **この手順書に書かれていないSQLを SQL Editor で実行しない。** これは `staff-registration-guide.md` 第9章からの、当社の変わらない約束です
6. ⛔ **`Confirm email` をONにしない**（第4部）
7. ⛔ **氏名で対象を指定しない。** 同姓同名の別人を消してしまいます。**必ずUIDで指定**します
8. ⛔ **仮パスワードを台帳・メモ・チャットの履歴に残さない**（3-2 ステップ3）
9. ⛔ **書き出したCSVを、個人の端末・私物のUSB・個人のクラウドに置かない**（2-6）
10. ⛔ **迷ったまま進めない。** 削除は取り消せません。**止めてオーナーに相談する**ことは、いつでも正しい選択です

# 付録B: 画面から削除できないときの代替手段

> ## 🛑 **この付録のSQLは、実行するとその会員のデータが全部消えます。取り消せません。**
>
> **使ってよいのは、第2部ステップ5（Authentication → Users → Delete user）がエラーになって進めない場合だけ**です。まずは画面からの削除を試してください。
>
> **使う前に、必ず次の3つを満たしていること:**
> 1. 第1部の本人確認が済んでいる
> 2. **第2部ステップ3の書き出し（CSV 3本）が保存済み**
> 3. 貼り付けるUIDが、2-5で確認した本人のものである

> #### 🔍 このSQLを実行すると何が起きるか
> 指定したUIDの**ログインアカウントを消します。** データベースの作りにより、それに連動して**会員情報・応募・スタッフの対応記録・お気に入り・同意の記録も、すべて自動的に消えます**（2-2の連鎖削除）。**元に戻す方法はありません。**

```sql
-- 【🛑 すべて消えます・取り消せません】この会員のログインアカウントと、
--    それにぶら下がる会員情報・応募・スタッフメモ・お気に入り・同意記録を削除する
delete from auth.users where id = 'ここにUIDを貼る';
```

実行後は、**必ず第2部ステップ6の確認SQLを実行し、5項目すべてが 0 であること**を確かめてください。

> エラーが出た場合は、**それ以上何も実行せず、エラーの文言をそのままClaudeに見せてください。**

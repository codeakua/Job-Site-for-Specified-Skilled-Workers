# 会員データの保管場所を東京へ移す手順（オーナー用・専門知識不要）

> **このガイドでできること**: 会員データを保管している Supabase を、**オーストラリア（シドニー）から東京へ**移します。
> - **所要時間**: 1〜1.5時間（待ち時間を含む）
> - **やる人**: サイトの管理者（Supabase と Vercel にログインできる方）
> - **費用**: かかりません（無料枠のまま）
> - 途中で迷ったら、**いま見えている画面の文字をそのままClaudeに伝えれば**（スクリーンショットでもOK）、その場で案内します。

---

## 1. まず知っておいてほしいこと（2分）

### Supabase は「引っ越し」ができません

Supabase には、**あとから保管場所（リージョン）を変える機能がありません。** プロジェクトは作られた場所に一生留まります。「組織の移動」という機能はありますが、これは保管場所を変えるものではありません。

つまり、**東京に新しいプロジェクトを作り直して、そちらに切り替える**のが唯一の方法です。

### たとえるなら

いまの状態は、**シドニーの貸金庫に会員名簿を預けている**ようなものです。金庫の場所は動かせないので、**東京の支店に新しい金庫を借りて、中身を移し、シドニーの金庫を解約する**——これが今回やることです。

### いまが一番ラクなタイミングです

本番の会員データがまだほとんどありません。**中身がほぼ空の金庫を借り直すだけ**なので、いま移すのが圧倒的に簡単です。会員が増えてから移すと、データの移し替え作業が必要になり、その間サイトを止めることにもなります。

## 2. 移す前に：本当に移すべきか（1分で判断）

| | 東京に移す | シドニーのままにする |
|---|---|---|
| 表示の速さ | **速くなる**（日本の利用者で往復が数百ミリ秒縮む） | 遅いまま |
| 法務書類の説明 | **1か国ぶん短くなる**（オーストラリアの法制度の説明が不要になる） | オーストラリアとアメリカの**2か国**の説明が必要 |
| 中国からのアクセス | 東京の方がやや有利 | — |
| 作業 | 1〜1.5時間必要 | 不要 |

> ⚠️ **ひとつ誤解しやすい点**: 東京に移しても、**「外国の会社に預けている」という事実は変わりません。** Supabase を運営している Supabase, Inc. はアメリカの会社だからです。個人情報保護法の「外国にある第三者への提供」は、**サーバーの置き場所ではなく、預け先の会社がどこの国の会社か**で判断されます。
>
> ### 📌 「外的環境の把握」も、東京に移せば不要になる——とは限りません
>
> 以前このガイドには「東京に移せば**外的環境の把握**（＝データが置かれている国の法制度を調べて対策する義務）が軽くなる」と書いていましたが、**これは正確ではありませんでした。訂正します。**
>
> この義務が発生する条件は**2つ**あり、①外国のサーバーに保存している場合**だけでなく**、②**外国の会社に取り扱いを委託している場合**も含まれます（個人情報保護委員会のQ&A）。当サイトはプライバシーポリシー第6条で Supabase, Inc. への「**委託**」だと明記しているため、**保管場所を東京にしても、委託先がアメリカの会社である限りアメリカが対象として残ります。**
>
> | 法務上の整理のしかた | 移設後に調べる必要がある外国 |
> |---|---|
> | **現在の案（同意をいただく方式）** | **アメリカ。減りません** |
> | もう一つの案（クラウド例外の適用） | 対象の外国が無くなります |
>
> つまり移設で確実に得られるのは、**オーストラリアの説明が1か国ぶん消えること**と、**もう一つの案（クラウド例外）を採れたときの効果が大きくなること**です。どちらの整理を採るかは**弁護士への確認論点 A-1・A-6** としてあり、当社の考えを書いたうえで意見を伺う形にしています。

**結論**: 速度が上がり、書類も1か国ぶん短くなるので、**移すことをおすすめします。**

## 5. 手順

### ステップ1：東京に新しいプロジェクトを作る（10分＋待ち時間）

1. https://supabase.com/dashboard を開きます。
2. **「New project」**（新しいプロジェクト）を押します。
3. 次のとおり入力します。

   | 項目 | 入力する内容 |
   |---|---|
   | Name（名前） | `yingpin-tokyo`（分かる名前なら何でも可） |
   | Database Password | **「Generate a password」を押して自動生成**し、**必ずコピーしてメモ帳などに保存**してください。あとから見ることはできません |
   | **Region** | **`Northeast Asia (Tokyo)`** ← **ここが今回の目的です。間違えないでください** |
   | Plan | Free（無料）のまま |
   | **GitHub (optional)** | **何も選ばない（空のまま）** ← 下記参照 |

   > ### ⚠️ **GitHub欄にリポジトリを選ばないでください**（実地で判明）
   > 画面が勝手にリポジトリを選んだ状態で開くことがあります。これは「リポジトリのSQLをSupabaseが自動で反映する」機能ですが、**このリポジトリはその形式になっていません**（Supabaseはリポジトリ直下の `supabase/` を見に行きますが、うちのSQLは `app/supabase/` にあり設定ファイルもありません）。繋ぐと**意図しないタイミングで自動処理が走るか、エラーが出続けます。**
   >
   > **解除の方法**: 選択済みの行をもう一度クリックすると外れます。外れない場合は **`F5` でページを再読み込み**すれば未選択に戻ります（**パスワードも作り直しになるので、控え直してください**）。作成後でも **Project Settings → Integrations → GitHub → Disconnect** で切り離せます。

4. **Security** の欄は次のとおりにします。

   | 項目 | 設定 | 理由 |
   |---|---|---|
   | `Enable Data API` | ✅ **チェックしたまま** | 外すとサイトがDBに接続できません |
   | `Automatically expose new tables` | ✅ **チェックしたまま** | 🚨 **画面には「無効化を推奨」と書かれていますが、今回は従わないでください。** うちの `setup.sql` は8つの表のうち7つでこの既定動作に任せる作りです。外すと**求人一覧すら表示されません。** 安全性は落ちません（8つ全部にRLSを個別にかけ、見せてはいけない採番カウンタは明示的に権限を落としています） |
   | `Enable automatic RLS` | ☐ **チェックしない** | `setup.sql` が8つの表すべてに個別にRLSをかけるため不要です |

5. **「Create new project」**を押します。
6. 準備が終わるまで**2〜5分**待ちます（画面に進み具合が出ます）。

> 💡 無料プランでは**プロジェクトを2つまで**持てます。いまのシドニーのものを残したまま東京のものを作れるので、**失敗しても元に戻せます。**

### ステップ2：データベースの中身を作る（10分）

1. 新しいプロジェクトの画面で、左メニューの **「SQL Editor」** を開きます。
2. パソコンでリポジトリの **`app/supabase/setup.sql`** をテキストエディタで開き、**中身をすべて選択してコピー**します（755行あります）。
   - GitHub から開く場合: リポジトリの `app/supabase/setup.sql` → 右上の「Raw」→ 全選択してコピー
3. SQL Editor に貼り付けて、右下の **「Run」** を押します。
4. 結果欄に **`setval` という列が出て、値が `1`** になっていれば成功です。

> ### 💡 **`Success. No rows returned` ではありません**（実地で判明）
> このSQLの**一番最後に値を返す命令**が「応募番号の採番カウンタを合わせる」処理なので、その戻り値が表示されます。応募がまだ0件なので **`1`（次の応募が1番になる）が正しい値**です。**エラーではありません。**

> このファイルは**何度実行しても安全**に作られています。エラーが出たら、**その文字をそのまま Claude に伝えてください。**

### 確認：中身が正しくできたか

表を目で数えるより確実なので、**SQLで一度に確認します。** SQL Editor で **「+」（新しいクエリ）** を押して、下を貼り付けて Run してください。

```sql
select
  (select count(*) from information_schema.tables
     where table_schema = 'public')                                    as "表の数(期待値 8)",
  (select count(*) from jobs)                                          as "サンプル求人(期待値 14)",
  (select count(*) from fields)                                        as "分野マスタ(期待値 11)",
  (select count(*) from members)                                       as "会員(期待値 0)",
  (select count(*) from pg_policies where schemaname = 'public')       as "アクセス制御ルール(期待値 13)",
  (select count(*) from pg_proc where proname = 'generate_member_no')  as "会員番号の採番関数(期待値 1)";
```

**`8 / 14 / 11 / 0 / 13 / 1` になっていれば完璧です。**

> ⚠️ **アクセス制御ルールの期待値は 13 です（14 ではありません）。** SQLの中に `create policy` は14行ありますが、`apps_self_insert` だけは最初に作ったものを**セキュリティ修正が削除して作り直す**ため、最終的に残るのは13本です。**13 という数字は、そのセキュリティ修正が効いている証拠**です。

> 💡 **表の数が 6 だった場合**は、コピーした範囲が足りていません（`setup.sql` の最後まで選択できていない可能性が高いです）。もう一度、ファイルの**先頭から末尾まで**すべてコピーしてやり直してください。参考までに、正しくできていれば次の8つが揃います。
>
> `staff_users` `fields` `members` `jobs` `applications` `favorites` `application_staff_notes` `member_no_counters`

### ステップ3：認証のセキュリティ設定をやり直す（15分）

⚠️ **この設定は新しいプロジェクトには引き継がれません。必ずやり直してください。** 忘れると、`1234` のような弱いパスワードで登録できてしまいます。

以降で開くURLは、**新しいプロジェクトのID**に読み替えてください（新しいIDは、新プロジェクトを開いたときのアドレス欄に出ています）。

#### 3-0. 【最重要】「Confirm email」がOFFであることを確認する

> 🚨 **ここを飛ばすと、新規登録が全員できなくなります。しかも原因が非常に分かりにくい形で起きます。**
>
> これまでこのガイドには「既定でOFFなので触らない」と書いていましたが、**新しく作ったプロジェクトでは最初からONになっている可能性があります**（実際、いまの本番プロジェクトは、過去にOFFへ**設定した**記録が残っています）。**「触らない」ではなく「自分の目でOFFを確認する」に改めます。**

1. `https://supabase.com/dashboard/project/<新しいプロジェクトID>/auth/providers` を開きます。
2. **開いた最初の画面の「User Signups」という区画**に **「Confirm email」**（メール確認）があります。
   - 📌 **実地で判明**: 以前は「Email」の行を開いた中にありましたが、**Supabaseの画面更新で最初の画面に移動しました。** 見つからない場合は「Email」の行を開いた中も探してください
3. **ONになっていたら、OFFにして「Save changes」を押してください。** すでにOFFならそのままで構いません。
4. ついでに同じ区画で次も確認しておくと確実です（すべて既定のままで構いません）。
   - `Allow new users to sign up` … **ON**（OFFだと誰も登録できません）
   - `Allow anonymous sign-ins` … **OFF**（当サイトは使いません）

> **なぜ致命的なのか**: このサイトは電話番号でログインする仕組みで、内部的に `@phone.yingpin.app` という**実在しないメールアドレス**を使っています。ONにすると Supabase は「確認メールのリンクを踏むまで登録を完了させない」動きに変わりますが、**そのメールは誰にも届きません**。
>
> さらに厄介なことに、登録を試した人のアカウントだけが**中途半端な状態で残る**ため、**その電話番号では二度と登録もログインもできなくなります**。テストで使った番号が使えなくなるだけでなく、公開後なら実在の求職者が締め出されます。

#### 3-1〜3-4. セキュリティ設定（4項目）

**`docs/ops/supabase-auth-policy-guide.md`** の手順を、**新しいプロジェクトに対して**もう一度実行します。設定するのは次の**4つ**です。

1. パスワードの**最低文字数**（`8`）を強制する
2. パスワードの**文字種**（`Password Requirements` を **`Letters and digits`**）を強制する ← **以前のガイドから増えた項目です**
3. 漏洩パスワードの拒否をONにする（**無料プランでは設定できません。下記参照**）
4. ログイン試行回数の制限を確認する（**値は変えず、控えるだけ**）

> 🚨 **3の「漏洩パスワードの拒否」には罠があります。** 無料プランではONにできないのですが、**スイッチは普通に押せてしまい、「Save」を押した瞬間に保存全体が失敗**します。このとき**同じ画面で設定した1・2（文字数・文字種）も巻き添えで保存されません**。画面には入力した値が残って見えるので、**成功したように錯覚します。**
>
> **必ず、スイッチをOFFに戻してから Save し、そのあとブラウザを再読み込み（F5）して `8` と `Letters and digits` が残っていることを確認してください。**

### ステップ4：スタッフを登録し直す（社員1人あたり10分）

管理画面 `/admin` を使う社員を、**新しいプロジェクトに登録し直します。**

> 🚨 **いつもの手順（社員本人にサイトから会員登録してもらう方法）は、いまは使えません。**
>
> `docs/ops/staff-registration-guide.md` の第3章は、社員本人に**本番サイトの登録ページ**から登録してもらう手順です。ところが**この時点では、本番サイトはまだ古いプロジェクト（シドニー）につながっています。** そのまま登録すると、アカウントは**古い方**にできてしまい、**新しいプロジェクトのユーザー一覧には何も現れません。** 気づかずに古い方のUIDを新しいDBに登録しようとすると、`violates foreign key constraint` というエラーで必ず失敗します。

**したがって、いまは `docs/ops/staff-registration-guide.md` の「付録A」の方法を使ってください。** Supabaseの画面で直接アカウントを作る方法なので、サイトを経由せず、切り替え前でも実行できます。

手順の要点は次のとおりです（詳細と、電話番号→内部用アドレスの変換表は付録Aにあります）。

1. **新しいプロジェクト**の **Authentication → Users** を開き、**Add user → Create new user** を選ぶ
2. **Email** 欄に、`p` ＋ 国番号 ＋ 電話番号 ＋ `@phone.yingpin.app` の形の**内部用アドレス**を入力する（記号は入れず数字だけを続けます。例: `+81` の `90-1234-5678` なら `p819012345678@phone.yingpin.app`）
3. **Password** 欄に、社員に伝えるパスワード（**8文字以上・英字と数字を両方含む**）を入力する
4. ⚠️ **「Auto Confirm User」（自動で確認済みにする）に必ずチェックを入れる** ← **入れ忘れるとログインできません**
5. 作成後、その行のUIDをコピーし、**SQL Editor** で職員名簿に追加する

```sql
insert into staff_users (id, email, name)
values ('ここにコピーしたUID', 'tanaka@example.co.jp', '田中 太郎');
```

6. **登録できたかを必ず確認する**（付録Bの確認用SQL）。「ログイン用の内部アドレス」に、その社員の電話番号の数字が入っていることを目で確かめてください。

> 💡 **切り替え（ステップ5）が終わったあとは、いつもどおり第3章の手順が使えます。** 次に社員を追加するときは、そちらを使ってください。

### ステップ5：サイトの接続先を切り替える（15分）

ここまでは**サイトに影響しません**。ここからが切り替えです。

**5-0. 【先に】切り戻し用に「古い値」を控える（2分）**

⚠️ **上書きする前に必ず控えてください。** これが無いと、問題が起きたときに元に戻せません。

> ### 🚨 **Vercelからは古い値を読み出せません**（実地で判明）
> このサイトの環境変数は **`Sensitive`（機密）** 指定になっており、**Vercelでは一度保存すると中身を再表示できません。** 編集画面のValue欄に薄い文字で `https://aBcDe.supabase.co` や `eyJhbGci…` と出ますが、**それはVercelが表示している入力例（ダミー）であって実際の値ではありません。**
>
> **したがって、古い値は Supabase 側から取り直します。**

1. **古いプロジェクトのキー**を控えます。下のURLを開いて、**`anon` `public`**（または `Publishable key`）をコピーし、メモ帳に「**旧キー**」として保存してください。
   ```
   https://supabase.com/dashboard/project/<古いプロジェクトID>/settings/api-keys
   ```
2. **古いURL**もあわせてメモします（形は決まっています）。
   ```
   https://<古いプロジェクトID>.supabase.co
   ```

これで、何かあっても元に戻せます。**ここが今回の唯一の保険です。**

**5-1. 新しい接続情報を控える**

1. 新しいプロジェクトで **Project Settings → API**（新しい画面では **API Keys**）を開きます。
2. 次の2つをコピーしてメモします。
   - **Project URL**（`https://〇〇〇.supabase.co` の形）
   - **anon public** と書かれたキー（`eyJ...` で始まる長い文字列）
     - Supabaseはキーの呼び方を変更中で、**`Publishable key`（`sb_publishable_...` で始まる）**と表示されることがあります。**その場合はそちらをコピーしてください。** どちらでも動きます。

> ## 🚨 絶対にコピーしてはいけないキー
>
> 同じ画面に **`service_role`**（サービスロール）または **`secret`**（シークレット）と書かれたキーがあります。**これは絶対に使わないでください。**
>
> このキーは**会員データの保護（アクセス制限）を完全に無視できる「マスターキー」**です。`NEXT_PUBLIC_` で始まる欄に入れると、**その値がサイトを訪れた誰にでも見える形で配られ、全会員の氏名・電話番号・住所・WeChat IDが誰でも読み書きできる状態**になります。
>
> **見分け方**: 名前に `anon` / `publishable` と書いてあるものが正解。`service_role` / `secret` と書いてあるものは**絶対に触らない**。

**5-2. Vercel の設定を書き換える**

> 📌 **画面の場所（実地で判明）**: 左メニューの **`Environment Variables`** です。**`Settings → Environments` は「環境の一覧」で別物**なので注意してください。次の直URLが確実です。
> ```
> https://vercel.com/<チーム名>/<プロジェクト名>/settings/environment-variables
> ```

1. **Environment Variables** で、次の2つを **5-1でコピーした新しい値に書き換え**ます（行をクリック → Value欄を貼り替え → Save）。

   | 名前 | 新しい値 |
   |---|---|
   | `NEXT_PUBLIC_SUPABASE_URL` | 新しい Project URL |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 新しい anon public（または Publishable）キー |

2. ⚠️ **環境（Environment）ごとに別々の値が登録されている場合があります。** 各項目に `Production` / `Preview` / `Development` というラベルが付いています。
   - **1つの登録に3つのラベルが全部付いている**場合 → その1つを直せば完了です。
   - **環境ごとに分かれて複数行ある**場合 → **`Production` を含む行は必ず直してください。** `Preview`・`Development` の行も、テスト用に使うなら同じく直しておくと後で混乱しません。

   > その他（`RESEND_API_KEY`・`STAFF_NOTIFY_EMAILS`・`UPSTASH_...`）は**そのままで構いません。**

**5-3. 再デプロイする（← これを忘れると切り替わりません）**

⚠️ **環境変数を保存しただけでは、いま動いているサイトには反映されません。** このサイトの接続先は、**サイトを組み立てる（ビルドする）ときに埋め込まれる**仕組みだからです。だからこそ、**組み立て直し（再デプロイ）が必須**になります。

> ### ⛔ 保存後に出る青い案内の「Redeploy」ボタンは使わないでください（実地で判明）
> 保存すると画面右下に **「A new deployment is needed for changes to take effect.」** という案内が出て、**Redeploy** ボタンが付いています。
> **このショートカットは使わないでください。** ビルドキャッシュを使ったまま再デプロイされる可能性があり、そうなると**古い接続先が埋め込まれたまま**になります。**「Dismiss」で閉じて、下の手順で進めてください。**

1. **Deployments** タブを開きます。
2. **`Production` という印が付いている行**を探し、その右端の **「⋯」** → **「Redeploy」** を押します。
   - ⚠️ **一番上の行が Production とは限りません。** ブランチのプレビュー用デプロイが上に来ていることがあります。**印を必ず確認してください。**
3. 確認画面に **「Use existing Build Cache」**（前回の組み立て結果を再利用する）というチェック欄があります。**このチェックは必ず外してください。**
   - ⚠️ **チェックが入ったままだと、古い接続先が埋め込まれたまま再利用され、「再デプロイしたのに切り替わらない」という状態になります。** 今回いちばん起きやすい失敗です。
4. **「Redeploy」** を押し、完了（緑のチェック）まで**1〜3分**待ちます。

### ステップ6：動作確認（10分）

**旧プロジェクトを消す前に**、必ず次を全部確かめてください。

> ## 🚨 なぜ「求人が表示された」だけでは確認にならないのか
>
> **新しいDBにも古いDBにも、まったく同じサンプル求人14件が入っています。** そのため「求人一覧が出た」「応募できた」「管理画面が開けた」は、**切り替えが失敗して古いDBを見たままでも、全部そのまま成功してしまいます。**
>
> この状態で次のステップ7に進んで旧プロジェクトを削除すると、**その瞬間にサイトが完全に停止し、削除は取り消せません。**
>
> そこで、**古いDBでは絶対に起きないこと**を先に確認します。

#### 6-1. 【最重要】新しいDBを見ていることの証明（3つ全部）

**① これまで使っていた会員アカウントでログインできないこと**

いつもテストに使っている会員の電話番号とパスワードでログインしてみてください。

- ✅ **ログインできない**（「電話番号またはパスワードが違います」等）→ **正解です。** 新しいDBには会員が1人もいないので、これが正しい反応です。
- ❌ **ログインできてしまう** → **切り替えができていません。** 古いDBを見ています。ステップ5をやり直してください（特に5-3のビルドキャッシュ）。

**② 管理画面の会員一覧が「0人」であること**

ステップ4で作ったスタッフのアカウントで `/admin` にログインし、**`/admin/members` を開きます。**

- ✅ **1人も表示されない** → **正解です。**
- ❌ **これまでのテスト会員が並んでいる** → **古いDBを見ています。** ステップ5をやり直してください。
- ❓ **そもそもスタッフでログインできない／「権限がありません」と出る** → これも**古いDBを見ているサイン**です。ステップ4で作ったスタッフは**新しいプロジェクトにしか存在しない**ため、古いDBを見ていると入れません。ステップ5をやり直してください。

**③ テスト登録したあと、会員一覧に「その1人だけ」が表示されること**

テスト用に新規会員登録をして、もう一度 `/admin/members` を開きます。

- ✅ **いま登録したテスト会員1人だけが表示される** → **正解です。**
- ❌ **他の会員も並んでいる** → **古いDBを見ています。**

> ### ⚠️ 「会員番号が `-1001` だから新しいDB」とは判断しないでください
>
> 会員番号は `YP-<日付8桁>-<4桁>` の形で、**その日の1人目は `-1001`** になります。一見これが新旧の見分けに使えそうですが、**使えません。**
>
> 番号を数える仕組み（`0004`）は**古いプロジェクトにも適用済み**で、しかもカウンタは**日ごとにリセット**されます。つまり**移設当日に古いDBで登録しても、その日の1人目なら同じく `-1001` になります。**
>
> **判断は必ず①②③（＝会員一覧の中身）で行ってください。** 会員番号は参考程度に留めてください。

> 💡 ①②③がすべて期待どおりなら、**確実に新しい東京のDBにつながっています。** ここまで来て初めて、旧プロジェクトを消してよい状態になります。

#### 6-2. ふつうの動作確認

1. サイトを開き、**求人一覧が表示される**
2. **6-1③で登録したテスト会員**でログインし、**求人に応募できる**
3. `/admin` にスタッフでログインし、**いま登録した会員と応募が見える**
4. **通知メールが届くことを確認する（2種類あります。別々の仕組みなので、必ず両方）**
   - **新規登録のお知らせ**（6-1③の登録で届きます）
   - **新しい応募のお知らせ**（上の2の応募で届きます）
   - 片方しか届かない場合も切り替えの失敗ではありません。届いていない方を Claude に伝えてください。

> 会員として既にログインしていた場合、**切り替えで一度ログアウトされます**（保存場所が変わるため）。これは正常です。
>
> 💡 **同じ電話番号で登録を何度もやり直すと、「しばらく待ってから」というエラー（5回/15分の制限）が出ます。** これは移設の失敗ではありません。15分待つか、別の番号でお試しください。

## 6. つまずきやすいところ

| 症状 | 原因と対処 |
|---|---|
| サイトが「求人が取得できません」と出る | ステップ5-3の**再デプロイを忘れている**ことがほとんどです |
| **再デプロイしたのに切り替わらない**（6-1で古いデータが見える） | **「Use existing Build Cache」のチェックを外し忘れた**可能性が最も高いです。もう一度、チェックを外して再デプロイしてください。それでも直らない場合は、`Production` の印が付いた行を選べているかを確認してください |
| 新規登録すると必ず失敗する | ステップ3-0の **Confirm email がON**になっている可能性。OFFに戻してください。**なお、一度この状態で登録を試した電話番号は使えなくなります**（別の番号でお試しください） |
| **同じ電話番号で登録できない／ログインもできない** | Confirm email がONの状態で登録を試した番号は、**中途半端なアカウントが残って使えなくなります。** Claude に伝えてください（Supabaseの Authentication → Users からその行を削除すると回復します） |
| 「しばらく待ってから」と出て登録できない | **5回/15分の制限**です。移設の失敗ではありません。15分待つか別の番号で |
| 管理画面に入れない | ステップ4のスタッフ登録が済んでいません。**サイトから登録した場合は古いプロジェクト側にできてしまっています**（ステップ4の警告を参照）。付録Aの方法でやり直してください |
| SQL実行で `violates foreign key constraint` | 職員名簿に入れようとしているUIDが、**新しいプロジェクトに存在しません。** 古いプロジェクトのUIDをコピーしていないか確認してください |
| Table Editor に表が6つしかない | `setup.sql` を**最後までコピーできていません**（ステップ2の確認を参照）。全選択してやり直してください |
| Region に東京が出てこない | 「New project」の作成中しか選べません。**作成後は変更できない**ので、間違えたらプロジェクトを削除して作り直してください |
| Database Password を控え忘れた | 通常の運用では使いません。必要になったら Project Settings → Database から再設定できます |
| API の画面に `anon` キーが見当たらない | Supabaseがキーの呼び方を変更中です。**`Publishable key`（`sb_publishable_...`）**を使ってください。**`service_role` / `secret` は絶対に使わないでください** |

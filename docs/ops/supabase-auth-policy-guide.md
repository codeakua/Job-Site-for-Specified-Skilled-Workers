# Supabase 認証セキュリティ設定ガイド（オーナー用・専門知識不要）

> **このガイドの目的**: Supabase の管理画面で **①パスワードの最低条件をサーバー側で強制** ②**漏洩パスワードの拒否** ③**ログイン試行回数の制限** を設定する。所要時間は約15分、1回だけの作業です。（GitHub Issue #31 の対応）
>
> **なぜオーナー操作なのか**: これはコードではなく **Supabase（会員データを保管しているサービス）の管理画面の設定**です。Claude はこの管理画面にログインできないため、あなたの操作が必要です。
>
> 途中で迷ったら、**いま見えている画面の文字をそのままClaudeに伝えれば**（スクリーンショットでもOK）、その場で案内します。

---

## なぜこの設定が必要か（1分で読める背景）

いまサイトには「パスワードは8文字以上」というチェックがありますが、これは**あなたのブラウザの中だけで動いている確認**です。

たとえるなら、**受付の人が「8文字以上ですね」と目視で確認しているだけで、金庫そのものには鍵がかかっていない**状態です。悪意のある人は受付を通らずに（＝ブラウザの画面を使わずに、プログラムで直接）データを送れるため、`1234` のような弱いパスワードでも登録できてしまいます。

今回の設定は、**金庫そのもの（Supabase）に鍵をかける**作業です。これで、どんな方法で登録しようとしても弱いパスワードは受け付けられなくなります。

---

## ⛔ 作業前に必ず読んでください（重要な禁止事項）

設定画面には、**触ると本番サイトが壊れる項目**が隣り合わせで並んでいます。

> ### 🚨 **「Confirm email」（メール確認）は絶対にONにしないでください**
>
> このサイトは**メールアドレスを使わない仕組み**（電話番号でログインし、内部的に `@phone.yingpin.app` という架空のアドレスを自動生成している）です。
>
> この項目をONにすると、Supabase が「確認メールを送って、本人がリンクを踏むまで登録を完了させない」動きに変わります。ところが**架空のアドレス宛のメールは誰にも届かない**ため、**新規登録が全員できなくなります**。既定でOFFになっているので、**そのまま触らない**でください。

その他、このガイドに書かれていない項目は変更しないでください。

   ```

## ① パスワードの最低文字数を強制する（約5分）

### 手順

1. 下のURLを直接開きます。
   ```
   https://supabase.com/dashboard/project/jqevswrbdbmxifauqhfi/auth/providers
   ```
   ※開けない場合: 左メニューの **Authentication**（認証）→ **Sign In / Providers**（サインイン／プロバイダ）。Supabaseの画面更新により **Providers** とだけ表示されていることもあります。

2. **「Email」** と書かれた行を探してクリックします（アコーディオンのように下に開きます）。

3. 開いた中に **「Minimum password length」**（パスワードの最低文字数）という入力欄があります。
   - ここに **`8`** と入力してください。
   - 既に `6` などが入っている場合は `8` に書き換えます。

   > ### ⚠️ **`8` より大きい数字にしないでください**
   > サイトの登録画面には「8文字以上」と表示されています。ここに例えば `10` を入れると、利用者が8文字で入力したときに、**画面には何も警告が出ないのに登録ボタンを押した瞬間に英語のエラーが出る**という、非常に分かりにくい状態になります。
   > 数字を変えたい場合は、サイト側の表示も合わせて直す必要があるので、先にClaudeにご相談ください。

4. すぐ下に **「Password Requirements」**（パスワードの要件）という選択欄があります。
   - ここを **「Letters and digits」**（英字と数字）に変更してください。
   - 選択肢が英語で複数並んでいます。**上から2番目**にあたる、`Lowercase, uppercase letters and digits` **ではない**方（大文字・小文字を区別しない、英字と数字だけを求めるもの）です。迷ったらClaudeに画面を見せてください。

   > ### ✅ **なぜ今回から変更してよいのか**
   > 以前この項目は「変更しないこと」としていました。サイト側が文字種をチェックしておらず、有効にすると**中国語の利用者に英語のエラーメッセージが突然出てしまう**ためです。
   > **PR-3（Issue #30・#35）で、サイト側の登録画面とサーバーの両方に「8文字以上＋英字と数字」の同じチェックを入れました。** 入力中に中国語（または日本語）で案内が出るようになったので、この設定と食い違わなくなりました。
   >
   > ⚠️ **これより厳しい `Lowercase, uppercase letters and digits`（大文字も必須）や `... and symbols`（記号も必須）は選ばないでください。** サイト側はそこまで求めていないため、画面には何も出ないのに送信時だけ英語エラーになります。
   >
   > 🕘 **順番**: PR-3 が本番にマージ（デプロイ）された**あと**に変更してください。先に変更すると、ごく短い間ですが上と同じ食い違いが起きます。

5. 一番下の **「Save changes」**（変更を保存）ボタンを押します。「Settings saved」等が表示されれば完了です。

   > 💡 **次の②「漏洩パスワードの拒否」も、実はこの同じ画面にあります。** 保存する前に②まで読んで、まとめて設定・保存すると1回で済みます。

### 確認方法
サイトの新規登録画面で、パスワードを **7文字以下**で登録しようとしてエラーになればOKです。
（画面のチェックで先に止められるので、正確な確認は次の「設定できたかの最終確認」で行います。）

> 💡 **既存の会員への影響はありません。** この設定は「これから設定されるパスワード」にのみ適用されます。今の会員がログインできなくなることはありません。

## ② 漏洩パスワードの拒否をONにする（約3分）

「漏洩パスワード」とは、過去に他社のサービスから流出して、**インターネット上に公開されてしまっているパスワード**のことです（`password123` など）。悪意のある人はそのリストを使って総当たりで侵入を試みます。

Supabase には、そうしたリストと照合して登録を拒否する機能があります。

> ### 📍 **この設定は①と同じ画面（Email プロバイダ設定）にあります**
> 「Attack Protection」（攻撃対策）というページにも `Prevent use of leaked passwords` という行が出てきますが、**そこにスイッチはありません**。状態表示（`DISABLED`）と、設定画面へ移動するためのボタンがあるだけです。
> **①を実施済みなら、その画面でこの②も一緒に済ませてしまうのが早いです。**

### 手順（①の画面から続けて行う場合）

1. ①で開いた **Email** の設定画面の中に、**「Prevent use of leaked passwords」**（漏洩パスワードの使用を防ぐ）という項目があります。スイッチを **ON** にします。

2. 一番下の **「Save changes」**（変更を保存）を押します。

### 手順（Attack Protection の画面から入ってしまった場合）

1. 左メニューの **Authentication** → **Attack Protection**（攻撃対策）を開くと、次の2項目が表示されます。

2. **「Prevent use of leaked passwords」の行の右端にある白いボタン「Configure in email provider」**（メールプロバイダで設定する）**を押します。**
   - その左隣の `DISABLED` は「現在オフです」という**状態表示で、押せません**。
   - ボタンを押すと①と同じ **Sign In / Providers → Email** の画面に移動するので、上の手順に合流してください。

3. ⛔ **同じ画面の上にある「Enable Captcha protection」（CAPTCHA保護）はOFFのままにしてください。**
   SupabaseのCAPTCHAは中国からの到達性が不確実なため、このサイトでは採用しない方針です。**この画面の「Save changes」ボタンはCAPTCHA用**なので、押す必要はありません。

> ### 🚨 **【実地で判明】無料プランではONにできません。しかも①の設定まで巻き添えで保存されません**
>
> **2026-07-27 の実施時に確認した実際の挙動**（想定と違ったのでそのまま記録します）:
>
> スイッチは**グレーアウトせず、普通に押せてしまいます**。ところが **「Save」を押した瞬間に**次のエラーが出て、**保存そのものが失敗**します。
>
> ```
> Failed to update auth configuration: Configuring leaked password protection
> via HaveIBeenPwned.org is available on Pro Plans and up.
> ```
>
> ⚠️ **ここが罠です。** Supabase はこの画面の設定を**まとめて1回で保存する**ため、漏洩パスワード保護が拒否されると、**同時に変更した①の「Minimum password length = 8」も一緒に保存されません**。画面には入力した `8` が残って見えるので、**成功したように錯覚します**。
>
> **対処**:
> 1. 「Prevent use of leaked passwords」のスイッチを押して**グレー（OFF）に戻す**
> 2. 「Minimum password length」が `8` であることを確認する
> 3. 「Save」を押し、**赤いエラーが出ないこと**を確認する
> 4. **ブラウザを再読み込み（F5）して、`8` のまま残っているかを必ず確認する**（`6` に戻っていたら保存できていません）
>
> 💡 **手順3で「Saveがグレーになって押せない」場合、それは正常です。** Supabaseの Save ボタンは**未保存の変更があるときだけ押せる**仕様なので、押せない＝**画面の内容がすでに保存済みの内容と一致している**という意味になります。そのまま手順4の再読み込み確認へ進んでください。
>
> **②はスキップして構いません。** Pro への切り替えは公開前の別作業（M2）で予定しているので、**そのタイミングでまとめてON**にします。今は無理に有料化しないでください。
>
> なお、①の最低文字数と、次のPR-3で入れる「登録回数の制限」がある状態なら、**公開時点でこれが無くても致命的ではありません**（多層防御の1枚が欠けている状態）。

### 確認方法
サイトの新規登録で、パスワードに **`password123`** と入力してみてください。エラーで登録できなければ成功です。
（※このテストで登録が通ってしまった場合は、設定が反映されていません。Claudeに伝えてください。）

## ③ ログイン試行回数の制限を確認する（約5分）

「1つのパスワードを何万回も試して当てる」攻撃を防ぐため、一定時間内の試行回数に上限を設けます。

### 手順

1. 下のURLを直接開きます。
   ```
   https://supabase.com/dashboard/project/jqevswrbdbmxifauqhfi/auth/rate-limits
   ```
   ※開けない場合: 左メニューの **Authentication** → **Rate Limits**（レート制限）。

2. 一覧の中に **「Rate limit for sign ups and sign ins」**（新規登録とログインの制限）という項目があります。
   - 「◯回 / 5分（per IP address）」のような形式で数値が入っています。

3. **今回は数値を変更せず、いまの値をメモして、このガイドの最後の記録欄に書き込むだけにしてください。**

   > ### ⚠️ **なぜ「厳しくしない」のか（重要）**
   > この制限は **IPアドレス（インターネット上の住所）1件あたり**でカウントされます。ところが**中国の携帯回線では、非常に多くの利用者が同じIPアドレスを共有している**のが普通です（CGNATという仕組み）。
   >
   > つまりここを厳しくしすぎると、**攻撃者ではなく、同じ回線を使っている普通の求職者が「回数オーバー」でログインできなくなる**という事故が起きます。しかも本人には理由が分からないため、そのまま離脱してしまいます。
   >
   > 攻撃対策の本命は、**電話番号ごとに数える制限**（PR-3で実装済み）です。IPで殴るのは副次的な手段と考えてください。既定値のままで問題ありません。
   >
   > 📌 ただし**この項目だけは残しておく価値があります**。サイトの登録画面を通さず Supabase を直接叩かれた場合、サイト側の制限は通らず、この Supabase 側の制限だけが効くためです。**下げず・消さず、既定のまま**にしておいてください。

4. 何も変更していないので、保存操作は不要です（値を変えた場合のみ **Save changes**）。

> ### 📌 将来のための申し送り：この制限は「緩すぎ」ではなく「厳しすぎ」に転ぶ可能性がある
>
> 既定値は **30回 / 5分（IPアドレスごと）** です。**β版の利用者数なら十分に余裕があります**が、上で説明したCGNAT（多数の利用者が同じIPを共有する仕組み）のため、**中国からの利用者が増えると、同じIPを共有する何十人分のログインが合算されて上限に達する**ことが理論上あり得ます。
>
> **もし「ログインできない」「登録できない」という問い合わせが複数の利用者から同時期に届いたら、まずこの設定を疑ってください。** その場合の対処は「この数値を**引き上げる**」であり、下げることではありません。総当たり攻撃への備えは、パスワードポリシー（①②）とPR-3の電話番号単位の制限が受け持ちます。
>
> 現時点では**変更せず、この可能性を記録しておくに留める**判断です（実際の利用者数が分からないうちに数値をいじると、かえって防御を弱めるため）。

## 設定できたかの最終確認（約3分）

> ### 📌 2026-07-27 時点の状況では、下記のサイト上のテストは不要です
> ②（漏洩パスワード保護）が無料プランのためOFFなので、`password123` は**登録が通るのが正常**であり、このテストでは何も判定できません。
> また①（最低文字数）は、サイトの登録画面が先に「8文字以上」を弾くため、**サーバー側の設定が効いているかをサイト経由では確認できません**。
>
> **したがって、現時点で①が保存できたかの確認方法は「Supabaseの画面を再読み込み（F5）して `8` が残っているか」だけです。** 下記の手順は、将来 Pro プランに切り替えて②をONにしたときに使ってください。

実際にサイトで試して、設定が効いていることを確認します。

1. サイトの新規登録画面を開きます。
   ```
   https://job-site-for-specified-skilled-work.vercel.app/register
   ```
2. **使っていない適当な電話番号**（例: 90-0000-0001）を入力して進みます。
3. パスワード欄に **`password123`**（12文字なので、文字数チェックは通ってしまう）と入力して登録を試みます。
4. **エラーになれば ② が正しく効いています。**
   - ②をスキップした（グレーで押せなかった）場合は、ここは登録が通ります。それが正常です。
5. テストで登録してしまった会員は、管理画面 `/admin/members` で確認できます。不要なら削除方法をClaudeにお尋ねください。

## この設定で変わること・変わらないこと

- **変わる**: これから登録する人・パスワードを変更する人に、最低文字数と文字種（英字＋数字）（と、②をONにした場合は漏洩パスワードの拒否）がサーバー側で強制される
- **変わらない**: 既存会員のログイン・サイトの見た目・応募や求人の動作
- **今回やらないこと**: 電話番号ごとの登録回数制限は **PR-3（Issue #30・#35）でサイト側に実装済み**。その回数を全サーバーで共有するための置き場所（無料）の申し込みは別ガイド → **`docs/ops/rate-limit-store-guide.md`**

システム設計と開発の進め方

モック（見た目の試作）を「実際に使えるサイト」にするための設計図です。専門知識がなくても読めるよう、例え話と図で説明します。

1モックとβ版のちがい

β版とは、モックの裏側に「金庫（データベース）」と「事務室（管理画面）」を付けたものです。

モック（完成済み）β版（これから作る）
見た目・操作感✓ ある✓ モックをそのまま使う
登録した情報✗ 保存されない✓ 本当に保存される
ログイン✗ 演出のみ✓ 本人だけ入れる
求人の登録・編集✗ 固定データ✓ スタッフが管理画面から自由に
応募の管理✗ できない✓ 一覧・状態管理できる

会員側の7画面はモックがそのまま設計図（移植するだけ）。新しく作るのは管理画面の5画面です。

5ログイン（認証）の方式

β版は「電話番号＋パスワード」で開始します
  • SMS送信なし → 追加費用ゼロ・最速で開始できる
  • 中国の番号（+86）はSMSが届かないことがある → SMSに頼らない設計はむしろ安全
  • なりすまし対策：登録 → スタッフがWeChatで本人確認 → 管理画面で「確認済み✓」にする運用
  • SMS認証は将来必要になったら後から追加できる設計にしておく

6応募データの流れ

WeChatでのやり取りは今まで通り人間の仕事。サイトは「集める・記録する・整理する」に徹します。

会員登録求職者

電話番号＋パスワードで登録 → 台帳に保存

通知メール自動

「新しい登録がありました」がスタッフに届く

WeChatで本人確認スタッフ

挨拶を兼ねて本人確認 → 管理画面で「確認済み✓」

求人を探して応募求職者

絞り込み → 詳細 → 応募ボタン。応募台帳に記録され、スタッフへ通知メール

案内・面接調整スタッフ

WeChatで詳細案内。進み具合を管理画面で更新（連絡済→面接→内定→入社）

7ClaudeとCodexの分担

設計と安全性はClaudeが一貫して担当し、仕様が明確な「量の多い」作業をCodexに割り振ります（コード量の目安 Claude 3.5：Codex 6.5）。

担当作業内容理由
🤖 Claude全体設計／データベースと安全設定／ログイン認証／共通ルール整備／CodexのPRレビュー／結合テスト設計と安全性は1人が一貫して持つべき領域
⚡ Codexモック画面の移植（一覧・詳細・お気に入り・マイページ）／管理画面の作成／中国語辞書の移行／単体テスト／小修正仕様が明確な量産作業。使用量に余裕がある方へ

↓

あなたの操作①
↓

📋 Codexへの依頼文（このままコピペして、#番号だけ変える）
GitHubの codeakua/Job-Site-for-Specified-Skilled-Workers を開いて、Issue #◯◯ を読んでください。リポジトリ直下の AGENTS.md のルールに必ず従って実装し、feature/Issue番号-内容 のブランチでPRを作成してください。AGENTS.mdで禁止されている範囲（データベース定義・共通ルールファイル等）は変更しないでください。

10リスクと対策

リスク対策
中国からの表示速度・接続Google系部品は不使用（対応済み）。公開後に実測し、遅ければ配信高速化（CDN）を追加
+86へのSMSが届かないβ版はSMSを使わない方式を採用（§5）
規約・プライバシーポリシーのレビュー待ちPhase 2 の間にClaudeがドラフトを作成し、先に顧問弁護士へ渡して並行で進める
2つのAIの編集衝突チケットごとの担当フォルダ制＋土台はClaude専任（§7）
中国在住者の直接募集の適法性「本人が自分の意思で登録・応募する」形。労働局届出と中国国内での宣伝方法の2点は顧問弁護士へ確認（β開発は確認を待たず進行可能）
